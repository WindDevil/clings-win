# studio

The twin's own layer: the double-click menu, the VS Code entry point, and the
built-in web editor. Written by hand (nothing here is generated by
`tools/sync_from_source.py`), and **optional** - delete the whole directory and
every exercise still compiles, runs and checks. `clings.cmd` notices the missing
directory and says so; that is what smoke-test step 22 verifies.

Learner-facing documentation is in the repository [README](../README.md); this
file is for whoever changes the code.

## Layout

| Path | What it is |
| --- | --- |
| `__main__.py` | `python -m studio open\|web\|menu`; `clings.cmd` reaches this module only for those three verbs and for a double-click with no arguments |
| `bridge.py` | **the only place that talks to the runner** |
| `menu.py` | what a double-click does: run the exercise, then offer the numbered menu |
| `vscode.py` | find VS Code, open the package root plus one exercise |
| `server.py` | the web editor's backend: stdlib `http.server`, `127.0.0.1` only |
| `paths.py` | confining a requested path to a directory the caller is allowed to read |
| `languages/` | what a language has to provide, and the two that do |
| `web/` | the front end, no build step |
| `tests/` | the test suite (excluded from the released package) |

## The one rule: talk to the runner through `--json`

`bridge.py` invokes `clings list|doctor|run|reset --json` and turns the JSON into
dataclasses. Everything above it - the server, the languages, the browser - sees
only those dataclasses. There is no import of the runner (it is a single script,
not a package), no parsing of its human-readable output, and no second copy of
"where do exercises live and what is in them".

Those `--json` flags are not part of upstream: they are added by
`RUNNER_PATCHES` in [`tools/sync_from_source.py`](../tools/sync_from_source.py).
Two consequences worth knowing before you touch either side:

- A field the studio needs must be added to the runner's `--json` output, not
  scraped from a printed line. That keeps the interface the runner's, and
  anything else with a shell can use it too.
- Each patch has to match its anchor **exactly once** or `make sync` raises.
  Upstream changing that code fails the sync loudly rather than silently
  generating a runner without `--json`.

## Adding a language

The editor is not C-only by construction: the browser asks
`/api/session` which languages exist and what each one can do, and adapts. C is
simply the only one that answers.

1. Write `languages/<name>.py` with a `Language` subclass - see
   [`base.py`](languages/base.py) for the shape.
2. Add an instance to `LANGUAGES` in [`languages/__init__.py`](languages/__init__.py).
   Files pick their language by longest matching extension (`for_path`); anything
   unclaimed gets `plain.py`, which is why a language nobody registered still
   opens, just without checks or completions.
3. Set `checks` / `completes` to `True` **only** if the methods really answer.
   The browser uses those flags to decide whether to offer the feature at all -
   a language that claims to check but returns `[]` would tell the learner "no
   problems" about a file nobody looked at.

`editor_mode` is a presentation hint, not an instruction: the client hands it to
CodeMirror as a MIME type, which resolves against the modes in `vendor/`
(`text/x-csrc` → `clike`, which covers C). An unrecognised value degrades to
plain text, so a new language needs no JavaScript at all. If it needs more than
that, extend `describe()`.

C's `check()` never parses C. It stages the exercise into a temporary directory
with the editor's buffer substituted for the file on disk and runs the compiler
with `-fsyntax-only` and the same flags `run` uses, so the editor's diagnostics
cannot disagree with what the learner gets when they press *run*. **Keep that
property if you add a language that compiles**: an approximate checker is worse
than none, because the learner will trust it.

## The front end

`web/index.html`, `web/app.js`, `web/ui.css` and `web/vendor/` are served as
files; there is no bundler, no transpiler and nothing to install. Everything
under `web/` is reachable at `/static/...`, and nothing outside it is
(`paths.resolve_within`). The page's CSP is
`default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'`:
no inline scripts, no `eval`, no CDN. A library that needs any of those cannot be
used here, which is deliberate — the editor must work offline, from a package
with no network and no npm.

Vendored components are pinned in [`web/vendor/README.md`](web/vendor/README.md),
including how to update them.

## Security model

The threat being defended against is another page in the same browser, not the
learner:

- the server binds `127.0.0.1` only;
- the page is served with a one-time token substituted into `index.html`, and
  every `/api/` call must carry it (header or `?token=`) **and** come from the
  same origin; both are compared with `secrets.compare_digest`;
- file reads and writes are limited to the files the runner listed for that
  exercise - the editor cannot address anything else, not even by traversal;
- request bodies are capped (`MAX_BODY`), and responses are `no-store`.

It is not a sandbox. The editor runs the same compiler `run` runs, so a learner
who pastes hostile code gets exactly what they would get from the command line.

## Tests

```sh
make test                                              # or:
python -m unittest discover -s studio/tests -t . -v
```

They run the real runner, the real compiler and the real exercises - a stub
would only agree with itself. `tests/harness.py` holds the scaffolding and no
cases: the shared fixtures, a live server on port 0, and

- `@unittest.skipUnless(harness.compiler_ready(), ...)` for anything that needs
  to compile, so the suite is meaningful on a machine with no toolchain;
- `harness.unchanged(target)` for anything that runs or writes through the
  runner, which restores the exercise (and `.clings/progress.json`) byte for
  byte afterwards. Without it a test run would leave the tree modified, and
  `make check` compares that tree against upstream.

The suite runs on both Windows CI jobs. It is **not** in the package:
`tools/package_windows.py` strips `tests/`, because it needs a checkout to be
meaningful and because running it rewrites exercises.

## Gotchas

- `python -m studio` needs the repository root on `sys.path`; `clings.cmd`
  provides that with `PYTHONPATH`. Running `python studio/server.py` directly
  will fail on the relative imports - that is intentional.
- `vscode.py` opens the **package root**, not just the file, so the C/C++
  extension finds `include/` (see the shipped
  [`.vscode/c_cpp_properties.json`](../.vscode/c_cpp_properties.json)) and runs
  with `--reuse-window`, so pressing `2` twice does not pile up windows. The
  folder stays even when a line number is asked for.
- Spawning the editor goes through `cmd /c` when the CLI is a `.cmd` shim (which
  is what the Windows installer ships): cmd.exe runs it in a console window
  nobody asked for, so `_spawn` passes `CREATE_NO_WINDOW`.
